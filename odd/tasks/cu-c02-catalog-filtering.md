# Plan: CU-C02 catalog filtering across BFF, Core, and Frontend

## Problem and approach

The current BFF contract exposes only paginated products and the Core exposes
only the paginated GraphQL query `products(page, pageSize)`. CU-C02 requires
catalog discovery by text, year, player count, category, and price range, plus
relevance-oriented ordering and an empty result set when nothing matches.

The selected approach is to run the OpenAPI Contract Planner first and define
the public BFF query parameters and their validation. The BFF will map that
contract to optional arguments on the existing Core `products` query,
preserving the current response shape and pagination compatibility. The Core
resolver will build one parameterized SQL query against `product_boardgame`,
apply filters before `LIMIT/OFFSET`, and keep the current product mapping and
`ProductPage` metadata. Once the contracts and required backend components are
defined and implemented, the Frontend Home will consume the BFF service
instead of using its static catalog source.

## Behavioral decisions

- Extend `products`; do not create `searchProducts`.
- Keep all new arguments optional so existing queries remain valid.
- Text search matches product name or publisher, case-insensitively.
- Year uses exact equality.
- Player filters match games whose supported range overlaps the requested
  range: `max_players >= minPlayers` and `min_players <= maxPlayers`.
- Category matches a category token in the persisted comma-separated field.
- Price filters compare `price_amount` inclusively.
- Relevance ordering preserves the existing `ORDER BY id` default unless an
  explicit sort argument is introduced by the implementation contract.
- No-match results return an empty `items` array with `total: 0` and
  `totalPages: 0`; this is not a GraphQL error.
- The OpenAPI Contract Planner owns the public BFF parameter names, HTTP
  validation responses, and REST-to-GraphQL mapping proposal before source
  implementation begins.
- The Frontend must consume only the BFF REST contract; it must not call Core
  GraphQL directly.
- BFF REST/OpenAPI query parameters use `snake_case`, including
  `min_players`, `max_players`, `price_min`, `price_max`, `year_published`, and
  `category_id`.
- Core GraphQL SDL arguments on `products(...)` use `camelCase`, including
  `minPlayers`, `maxPlayers`, `priceMin`, `priceMax`, `yearPublished`, and
  `categoryId`.
- The BFF maps REST `snake_case` parameters to Core GraphQL `camelCase`
  arguments and transforms GraphQL `camelCase` responses back to REST
  `snake_case`.

## Scope and constraints

- Modify the BFF/Core contracts and implementations, their tests and READMEs,
  the Frontend Home and its integration tests/mocks/types, and the ODD task
  record.
- Keep the Frontend limited to the approved BFF REST contract; do not add
  direct Core GraphQL calls.
- Use parameterized SQL and preserve explicit validation for pagination and
  invalid filter ranges.
- Follow the existing minimal Graphene/Django style; do not add repositories or
  abstractions for a single query.

## Implementation record (supersedes stale plan assumptions)

The original decisions above remain the historical CU-C02 scope. The
implementation differs from the initial plan in these verified ways:

- The Frontend is integrated with `GET /api/v1/products`; it is not a static
  or mock-only catalog. It uses generated OpenAPI TypeScript definitions and
  covers loading, error, empty, and success states.
- The BFF validates REST `snake_case`, maps to GraphQL `camelCase`, maps the
  response back to `snake_case`, returns `502` for upstream GraphQL failures,
  and allows CORS from `http://localhost:3000` and
  `http://127.0.0.1:3000`.
- Core filtering is implemented with parameterized SQL before count and
  pagination. The local category map is limited to `1` strategy, `2`
  thematic, and `3` family; no migration was added.
- The planned relevance ordering is not implemented. The UI requests the
  first page with `page_size=100` and does not expose pagination controls.
