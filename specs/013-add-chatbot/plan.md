## Summary

Provide in-app buyer FAQ help grounded in reviewed, approved public knowledge and current catalog recommendations. The BFF owns the shop-scope guard, LangChain orchestration, ChromaDB retrieval, and the consumer REST boundary. Core owns conversation persistence and ownership enforcement in PostgreSQL. The browser never calls Core directly. Conversation content and dynamic catalog results are never added to ChromaDB.

## Request, Authentication, and Ownership

The browser sends chat requests only to the BFF. Registered-user ownership derives from the current bearer-authenticated Core user, not token claims supplied as owner metadata. The BFF does not locally verify JWTs or currently hold a trusted user ID; it must query Core's `me { id }` with the caller's bearer credential and use the ID returned by Core as the stable authenticated principal. It must not use the raw or caller-rotatable bearer token as a quota key. The Core interface was confirmed read-only at `bgg-shop-core/specs/schema.graphql:429`, `bgg-shop-core/saleor/graphql/api.py:1174-1176` and `:1359-1364`, and `api.py:2209-2219` (`AuthUser.id` is required). Anonymous browser continuity uses a BFF-issued opaque `chat_session` cookie with `HttpOnly`, `SameSite=Lax`, and `Secure` outside local development. The cookie alone identifies an anonymous quota session: a newly issued or rotated cookie is a new session, and no IP-based limiter is used. If a bearer token is supplied, that authenticated user scope is authoritative; it is not merged with or switched to the anonymous scope. No BFF or Core request accepts a caller-supplied owner ID. A missing, expired, or differently owned conversation is represented uniformly as not found so existence and metadata are not disclosed.

For anonymous requests, the browser sends only its `chat_session` cookie to the BFF. The BFF creates a fresh, short-lived HMAC-SHA256 JWT assertion for each internal Core call and sends it only in `X-Chat-Assertion`; that header and assertion are not part of the browser-facing API, are not accepted from the browser, and are never returned to it. The assertion uses `alg=HS256` and `typ=chat-assertion`, with `iss=bgg-shop-bff`, `aud=bgg-shop-core`, `sub` equal to the SHA-256 digest of the cookie value (never the raw cookie), `scope=chat:conversations`, `iat`, and `exp=iat+60s`. BFF and Core use the dedicated `CHAT_ASSERTION_SECRET` environment setting; it must not reuse JWT `SECRET_KEY` or `OPKEY_INTERNAL_SECRET`, and its value must never be recorded in plans, logs, or contracts.

Core validates the signature and algorithm, token type, issuer, audience, required scope, and expiry before deriving anonymous ownership exclusively from the validated `sub`. This is a short-lived, scoped assertion, not a one-time credential; replay prevention is not promised. Rotate the key by coordinating replacement of the BFF and Core environment values, without recording either value. When a registered-user bearer token is present, that authenticated user remains authoritative; the anonymous assertion is not an identity fallback or switch. Existing operation-key delegation remains limited to privileged staff operations and does not identify an anonymous buyer.

Staff receive no additional chatbot capability: only approved public knowledge and current public catalog reads are available. No account, order, administrative, or mutation tool is exposed.

## Approved Knowledge, Provider, and Data Security

- The team reviews and approves each FAQ, policy, or allowed public source before ingestion into ChromaDB. Updates and withdrawals require renewed review; ingestion operates only on the curated BFF-repository corpus. Keep source title/link metadata for grounded responses.
- Use local Ollama with `deepseek-r1:8b`; provider configuration contains no credentials in plans, examples, or contracts. Provider failures produce sanitized recoverable responses.
- For each submission, validate length and apply the BFF application guard before retrieval, model, catalog, Core, or persistence calls. Never echo protected source text. Invalid or out-of-scope requests are not persisted.
- Persist only permitted in-scope user/assistant exchanges in Core PostgreSQL. Do not persist provider prompts, hidden chain state, credentials, personal/order content, or arbitrary request metadata. Limit model context to the preceding 10 turns.
- Return only approved source metadata and current product facts returned by Core. Catalog results are transient response/context data and are never ingested into ChromaDB.
- Every chat response is `Cache-Control: no-store`; errors use stable public codes and messages and never include upstream exception text, traces, URLs, credentials, or submitted content.
- Core retention is 30 days from the last persisted activity. Explicit deletion and expiry remove only that conversation and its messages; ChromaDB has an independent reviewed-content lifecycle.

## Canonical BFF REST Contract

All paths below are consumer-facing and planned only; no Flask route or service behavior is added by this gate. The browser-facing anonymous credential is only the opaque `chat_session` cookie; `X-Chat-Assertion` is strictly BFF-to-Core transport and is never a browser request field or response value. The BFF applies the shared limit of 10 requests/minute per authenticated user or anonymous browser session. All responses are non-cacheable.

- `POST /api/v1/chat/conversations`: create a server-generated empty conversation for the authenticated buyer or an anonymous browser scope; issue `chat_session` for a new anonymous scope. No owner ID or assertion is accepted from the browser. Returns `201` with the conversation; may return `401`, `429`, or sanitized `503`.
- `GET /api/v1/chat/conversations/{conversation_id}`: read only the caller's conversation and persisted messages. Returns `200`; missing, expired, or cross-scope IDs all return the same `404`; invalid/missing identity is `401`; rate limit is `429`; upstream failure is sanitized `503`.
- `POST /api/v1/chat/conversations/{conversation_id}/messages`: accepts `{ "message": string }`, 1–2,000 characters. Applies shop guard before all retrieval/model/catalog/Core operations, and supplies at most 10 previous turns to the model. Returns answer, approved sources, and current Core-backed recommendations without echoing the submitted text. Invalid input is `400`; invalid identity is `401`; missing/expired/cross-scope conversation is `404`; rate limit is `429` with `Retry-After`; unavailable dependencies return sanitized `503`.
- `DELETE /api/v1/chat/conversations/{conversation_id}`: delete the caller-owned Core/PostgreSQL conversation only. Returns `204`; missing, expired, or cross-scope ID is `404`; invalid identity is `401`; rate limit is `429`; failure is sanitized `503`. ChromaDB is unaffected.
- `ChatMessage`, `ChatSource`, `ChatConversation`, `ChatReplyResponse`, and `ChatErrorResponse` in the canonical OpenAPI define transcript, source metadata, response-only Core product recommendations, expiry, and safe errors. No browser request or response includes an owner identifier or `X-Chat-Assertion`.

## Canonical Core GraphQL Contract

The minimal addition to `bgg-shop-core/specs/schema.graphql` defines:

- `Query.chatConversation(id: ID!)` for caller-owned conversation lookup.
- `Mutation.createChatConversation`, `recordChatExchange(conversationId, userMessage, assistantMessage, sources)`, and `deleteChatConversation(conversationId)`.
- `ChatConversation`, `ChatMessage`, `ChatSource`, `ChatConversationPayload`, and sanitized `ChatConversationError`/`DeleteChatConversationPayload` types.
- No owner ID input. For anonymous calls, the Core transport adapter receives `X-Chat-Assertion` from the BFF, verifies the approved assertion profile above, and exposes only its validated `sub` as the anonymous principal to GraphQL. The header is not a GraphQL argument. If a registered-user bearer token is present, that authenticated user is authoritative. Missing/expired/cross-owner IDs return `NOT_FOUND`. Content expires after 30 days of inactivity. Conversation persistence/deletion is independent of ChromaDB.

The SDL documents the internal transport/authentication boundary without exposing the assertion as a browser payload or GraphQL argument. T008 implements a subset of the Core runtime fields; the later `deleteChatConversation` implementation is covered by T025's DB-backed tests. Full runtime SDL conformance remains pending.
