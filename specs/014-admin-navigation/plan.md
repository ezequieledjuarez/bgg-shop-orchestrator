# Implementation Plan: Admin Navigation and Discoverability

**Branch**: `014-admin-navigation` | **Date**: 2026-11-09 | **Spec**: [spec.md](spec.md)
**Status**: Implemented and locally verified for the scoped feature slice. See [quickstart.md](quickstart.md) for unit, browser, and isolated service-path evidence and limitations.

## Summary

Make existing administrative work discoverable from the storefront and keep a shared, role-aware navigation shell across existing admin routes. Reuse product creation, coupon management, and Superadmin privilege management. The Frontend gets a fresh in-memory role snapshot from `GET /api/v1/auth/me`; the BFF resolves current state through existing Core `Query.me`. T006 promoted the approved endpoint design to canonical BFF OpenAPI, T007 observed endpoint tests fail before implementation, and T008 implemented the endpoint. Frontend generated types, guarded navigation, styling, browser checks, and scoped isolated service-path verification are complete. The design fragment in `contracts/admin-session.openapi.yaml` is retained as a non-canonical design copy.

Also style every existing admin screen as a coherent extension of the storefront. The user grants visual discretion, not approval of exact pixels. The Frontend navigation and styling implementation is complete; its local test and isolated integration evidence is in [quickstart.md](quickstart.md).

## Admin Screen Styling Approach

- **Grounding**: `src/index.css` and `src/App.css` contain warm off-white backgrounds, dark brown/charcoal text, terracotta accents, sans-serif body text with serif headings, rounded white cards, and existing `primary-button`/`purchase-form` patterns. Their font declarations differ; future inventory must use the current computed storefront typography rather than assume a single canonical font token already exists. `SalesPanel.css` and `UserManagementPanel.css` already provide bounded panel widths and local presentation.
- **Proposed direction**: Reuse those existing color values/patterns where contrast permits, with a consistent spacing rhythm, readable admin heading scale, restrained card surfaces, and clear primary/secondary/destructive treatments. These are design choices within authorized discretion, not a user-approved mockup. No mandatory mockup sign-off is needed; ask only for a genuine unresolved decision.
- **Implementation boundary**: Prefer scoped shared admin CSS and existing module classes; reconcile the two panel-specific styles without global storefront regressions, new UI/font dependencies, a token framework, or a component/design-system rewrite. Avoid added fetches, layout-measurement code, or unnecessary React state for presentation.
- **Coverage**: Products list/form/inventory; promotions list/form/price preview; coupons list/form; gift-card generation/result; audit filters/table/pagination; sales filters/summaries/tables/chart; reviews queue/actions; users search/list/privilege editor. Include headings, cards, buttons, forms, tables/lists, existing confirmations and success/validation/loading/error/empty states wherever present. Do not add a confirmation workflow or operation where none exists.
- **Responsive/accessibility acceptance**: Test 1280×720 (explicit configured base viewport), 768×1024, 375×812, and 320×720 (the existing body minimum width) with explicit browser viewport overrides, since Desktop Chrome project defaults may differ. Shared layout persists on route changes/direct loads; no clipped action or page-wide overflow. Wide tables may scroll locally with labels and keyboard access. Preserve labels/focus/announcements and measure WCAG AA text contrast (4.5:1 normal, 3:1 large) and non-text UI contrast (3:1); inherited colors are not automatically compliant.
- **Sequence**: T013 inventories current surfaces and adds deterministic failing presentation/accessibility assertions where meaningful. T014 applies shared/panel styles without touching role or route semantics. T015 verifies that presentation locally with fixtures or authorized local accounts. T011 attaches the common presentation to the new persistent protected shell only after its existing dependencies; T012 integrates both tracks and checks US6 with the protected routes. The approved design does not bypass canonical-contract or behavior dependencies or justify unsafe access.

## Contract and Endpoint Gate

The approved design uses the following REST endpoint to safely obtain current role flags:

| Method and path | Request | Approved response design | Approved authorization design |
|---|---|---|---|
| `GET /api/v1/auth/me` | No body or query parameters | `200` with `{ "is_staff": boolean, "is_superuser": boolean }`; `Cache-Control: no-store` | Bearer-authenticated active account; no operation-key-only access. Flags are read from current Core account state. |

The planning OpenAPI fragment is in `contracts/admin-session.openapi.yaml` and remains **non-canonical**. T006 promoted the approved operation to `bgg-shop-bff/specs/openapi.yaml` and validated it locally. T008 maps missing, invalid, or inactive bearer identity to sanitized `401`, failed Core identity resolution to sanitized `502`, and sets `Cache-Control: no-store` on all outcomes. No new Core GraphQL endpoint was needed; BFF reuses `Query.me`.

**Verification evidence and limits**: BFF tests cover valid current flags, active Superuser with `is_staff=false`, ordinary buyer, missing/invalid/inactive identity, malformed Core result, and sanitized upstream failure; the focused local suite passed. Frontend tests and mocked Chromium cover loading/error fail-closed behavior, role-specific links, shell persistence, direct navigation, session changes, and responsive/accessibility behavior. A scoped isolated live Frontend→BFF→Core current-user path also passed. Full live CRUD across all modules and full Core migration bootstrap are not verified; see [quickstart.md](quickstart.md). The Core contract/schema remains unchanged.

## Risks and Mitigations

- **Stale or fabricated role data**: Never infer privileges from token presence or browser storage. Fetch a current server projection on admin entry and session changes; keep backend checks authoritative.
- **Unauthorized user-management discovery**: Hide the personnel link except for `is_superuser=true`, including Superadmins with `is_staff=false`. Do not narrow other operational modules.
- **Information flash during loading/failure**: Render no admin links or protected panel data until role resolution succeeds. On denial, clear the in-memory snapshot and show a generic access state.
- **Contract drift**: T006 canonical OpenAPI validation is complete; T009 must generate Frontend types from that canonical contract before Frontend behavior implementation.
- **Duplicate functionality**: Existing product, coupon, and privilege flows are the targets; do not create replacement forms, routes, or CRUD.
- **Partial or inconsistent styling**: Inventory all eight modules, reuse current storefront patterns through scoped admin CSS, and verify form/list/feedback states, long content, chart/table layouts, and mobile actions rather than styling only navigation or initial examples.
- **Unverified inherited contrast or CSS leakage**: Measure actual text/UI/focus contrast pairs and recheck storefront regressions; no broad selector rewrite or new design-system architecture is required.
